# MeterMind — 3-Day / 15-Commit Plan

**Rule:** five meaningful commits per day, 15 total. Commit numbers are the sequence, not a promise to finish without debugging. The user makes each Git commit after reviewing the diff and test results. Do not squash them together.

## Day 1 — Working project foundation (Commits 1–5)

### 01 — `docs: add MeterMind product and AI workflow specs`
**Goal:** merge `SKILL.md`, `AGENTS.md`, product/architecture/database guidance, this commit plan and definition of done into the existing repo. Make README explain what is real vs simulated.

**Expected files:** `SKILL.md`, `AGENTS.md`, `docs/*`, updated `README.md`.

**Acceptance:** project scope and 15-step plan are documented; initial project generated by Spring Initializr is preserved; no application code is regenerated. `git status` is clean except for these intended changes after user commits.

**Learn:** repository instructions, project scope and small commits.

### 02 — `ci: add Maven verification workflow`
**Goal:** add GitHub Actions CI with Java 21, Maven Wrapper and a MySQL 8.4 service; run `clean verify` on pushes and pull requests.

**Expected files:** `.github/workflows/ci.yml`; workflow-specific README note if needed.

**Acceptance:** YAML parses; permissions are least-privilege (`contents: read`); DB test credentials are disposable values only; job waits for MySQL health; it invokes the repository's actual Maven wrapper. If starter code's Spring context requires config, provide the CI environment variables needed for it. Do not add release publishing yet.

**Learn:** CI, workflow triggers, services and build caching.

### 03 — `build: configure MySQL and Flyway local development`
**Goal:** configure datasource through environment variables, document local MySQL setup, add a local-only Compose service and ensure Flyway's MySQL module aligns with the project's Boot/Flyway version.

**Expected files:** `pom.xml` only if dependency is missing, `application.yml` or existing properties file, `docker-compose.yml` (or agreed location), `.env.example`, `.gitignore`, setup docs.

**Acceptance:** application can connect to local MySQL when credentials are supplied; `.env` and secrets are ignored; the app has no hard-coded real credentials; Flyway is configured; schema validation is used once migrations/entities exist. Keep the current generated configuration style if there is a good reason.

**Learn:** JDBC datasource, environment variables, migrations and local services.

### 04 — `feat(auth): add tenant-scoped identity and login roles`
**Goal:** add organization/user persistence and Spring Security using hashed passwords; support OWNER/BILLING_ADMIN/CUSTOMER roles and a clear local onboarding/demo strategy.

**Expected files:** identity/organization modules, security configuration, templates/controllers or account-provisioning code, Flyway migration, tests.

**Acceptance:** login/logout works; unauthenticated protected routes require login; password hashes, not raw passwords, are persisted; an owner is associated with an organization; authorities are explicit; no public endpoint allows role self-escalation; tests prove basic role protection. Keep account/customer linkage straightforward and explain it.

**Learn:** filters, `SecurityFilterChain`, `PasswordEncoder`, roles, principal and tenant.

### 05 — `feat(catalog): add plans and feature credit pricing`
**Goal:** owner-scoped plans and per-feature integer credit prices; expose only the CRUD/read path required by the MVP.

**Expected files:** `catalog` entities/repository/service/controller/DTOs, templates if appropriate, Flyway migration, validation and tests.

**Acceptance:** only an owner/admin from the same organization can manage a plan; credit price and monthly credits cannot be negative; monthly money price uses `BigDecimal`/MySQL `DECIMAL`; duplicate feature codes are rejected within the chosen scope; pricing queries are tenant-scoped.

**Learn:** JPA relations, validation, DTOs and unique constraints.

## Day 2 — Correct credit accounting (Commits 6–10)

### 06 — `feat(customers): add customer accounts and subscriptions`
**Goal:** owner can create customers and assign a plan/subscription with billing-period dates/status.

**Expected files:** customer/subscription modules, migration, form/API, tests.

**Acceptance:** records always belong to the owner’s organization; cross-organization plan/customer combinations are rejected; date range/status are validated; customer ownership is tested. If login linking is incomplete, document the temporary demo path and do not expose another tenant's records.

**Learn:** entity relationships, service validation and DTO boundaries.

### 07 — `feat(wallet): add grants and append-only credit ledger`
**Goal:** create one wallet per customer, owner-issued grants/adjustments with required reason and append-only ledger entries.

**Expected files:** wallet module, migration, tests and a simple owner action/endpoint.

**Acceptance:** unique wallet per customer; grant and ledger are atomic; grant records actor, amount, reference and balance-after; amounts are positive integer credits; corrections are new compensating entries rather than edits. Only authorized users can issue grants.

**Learn:** transactional service methods and audit ledgers.

### 08 — `feat(wallet): implement atomic debit and balance locking`
**Goal:** implement service-level credit consumption with insufficient-balance protection and concurrency control.

**Expected files:** wallet service/repository, domain exceptions, integration tests.

**Acceptance:** wallet lock or another proven atomic mechanism prevents overspending; wallet balance and ledger changes commit/rollback together; a wallet with 100 credits rejects a charge of 101 without side effects; a concurrent pair of 80-credit debits against 100 credits results in exactly one success and balance 20.

**Learn:** `@Transactional`, database locks, rollback and race conditions.

### 09 — `feat(usage): add idempotent usage events and API`
**Goal:** accept a customer usage request, resolve server-side pricing, store price snapshots, debit credits and return current balance.

**Expected files:** usage module, migrations/constraints, request/result DTOs, API errors and tests.

**Acceptance:** positive units only; price is resolved from the authenticated customer's active plan; `unit_credit_cost` and `credits_charged` are saved; same key + same payload is replay-safe; same key + different payload returns conflict; DB uniqueness handles concurrent duplicate requests; event, debit and ledger stay atomic.

**Learn:** REST endpoint contracts, idempotency, database uniqueness and request hashes.

### 10 — `test(security): verify tenant isolation and billing invariants`
**Goal:** close critical authorization/testing gaps before building dashboards.

**Expected files:** tests, small security/service fixes, CI configuration if needed.

**Acceptance:** tests prove customer A cannot read customer B's wallet/history, one organization cannot manage another's plans/customers, caller cannot set the price, failed consumption has no event/ledger side effect, and all integration tests run against MySQL in CI. Include the replay and concurrent debit cases from earlier commits in the regression suite.

**Learn:** integration tests, MockMvc/security test setup and regression testing.

## Day 3 — Insight, billing preview and delivery (Commits 11–15)

### 11 — `feat(ui): add owner and customer dashboards`
**Goal:** Thymeleaf dashboards show correctly scoped balances, daily usage, feature breakdown, recent activity and owner customer summary; use Chart.js if useful.

**Expected files:** owner/customer controllers or view models, templates, CSS/JS, tests where practical.

**Acceptance:** owner sees only their organization; customer sees only their account; values come from persisted data, not fabricated arrays; empty states are handled; core pages work at desktop width and are usable on mobile.

**Learn:** MVC model attributes, template fragments, view models and charts.

### 12 — `feat(alerts): add configurable usage thresholds and notifications`
**Goal:** save enabled alert rules and create deduplicated in-app notifications when credit/usage thresholds are crossed.

**Expected files:** alerts module, migrations, services and tests; UI for alerts if feasible.

**Acceptance:** rule thresholds are validated; evaluate on usage/balance changes; repeated evaluations do not generate unlimited duplicate alerts; customer/owner visibility follows tenant rules; zero balance blocks new usage independently of notifications.

**Learn:** event-triggered domain logic and idempotent notification records.

### 13 — `feat(insights): add runway forecast and explainable recommendations`
**Goal:** estimate days until depletion and generate a small rule-based set of recommendations from real usage history.

**Expected files:** insights module, queries/DTOs, customer view and tests.

**Acceptance:** forecast includes measurement window and assumption; handles zero usage, no history and insufficient sample size; rounding is documented; recommendations cite the feature/usage observation behind them; no fabricated savings or claims that an AI model is used.

**Learn:** analytics aggregation, deterministic rules and edge-case testing.

### 14 — `feat(billing): add invoice previews and renewal simulation`
**Goal:** create invoice preview/lines from the subscription fee and supported chargeable items; model renewal period/included-credit grant idempotently.

**Expected files:** billing module, migration, preview endpoint/page, renewal service and tests.

**Acceptance:** money uses `BigDecimal` and explicit scale/rounding; invoice line totals reconcile to subtotal; preview is clearly labelled simulated/draft; repeat renewal job invocation cannot grant the same period credits twice; no claim is made that a real payment or tax calculation occurred.

**Learn:** financial arithmetic, invoice snapshots and idempotent scheduled operations.

### 15 — `ci(release): build and publish tagged container images`
**Goal:** add a non-root multi-stage Dockerfile, harden docs and a GHCR release workflow triggered only by version tags.

**Expected files:** `Dockerfile`, `.dockerignore`, `.github/workflows/release.yml`, README release instructions and final checks.

**Acceptance:** Docker build succeeds; runtime image runs as non-root; secrets are environment-injected; CI remains green; a `v*` tag workflow can build and publish to `ghcr.io/<owner>/<repo>` using `GITHUB_TOKEN` with `packages: write`; README explains version tagging and how to pull/run an image. Do not deploy to an unspecified live host.

**Learn:** multi-stage images, least privilege, release tags and continuous delivery.

## End-of-day routine

After each group of five commits:
- inspect `git log --oneline -5` and `git status --short`
- run `clean verify`
- check the CI run in GitHub (if pushed)
- update the progress checkboxes below
- write 3–5 sentences in your own words about what you learned
